# 券的口径

本文说明「券包体检」与「用券排程」是怎么算的。所有假设写在这里，不藏在代码里。

> **先分清三种「省」，不要相加。** 本文讲的是**券后省**（`calculate-price` 返回的
> `discount`，单位分）。另外两种是**结构省**（同一批商品换买法的价差，见
> `adviser.py --intent`）和**标价差**（门店划线价 − 现价，见 `adviser.py --discounts`）。
> 三者口径不同，混着说就会得出一个谁也对不上的数字。

对应实现：[`scripts/coupon_doctor.py`](../scripts/coupon_doctor.py)
数据快照：[`data/raw/coupons_1420762.json`](../data/raw/coupons_1420762.json)、
[`data/raw/coupon_probe_1420762.json`](../data/raw/coupon_probe_1420762.json)、
[`data/raw/orders_summary_1420762.json`](../data/raw/orders_summary_1420762.json)

## 一、为什么券值得单独算

`available-coupons` 返回的券**只有名字和图片，没有面值**。而券名里往往也没有数字：

```
中薯条买一送一     → 值多少钱？
王牌小食拼        → 值多少钱？          ← 名字里没有数字，菜单里也没有对应商品
9.9元中杯冰美式    → 值多少钱？
```

所以"我有一堆券"这句话本身不含信息。要它变成能行动的东西，必须先回答**每张券值多少钱**。

## 二、券价值：三条来源，优先级严格

| 优先级 | 来源 | 做法 | 适用 |
|---|---|---|---|
| 1 | `probe` | 把券自带的商品码 + `couponId` + `couponCode` 传给 `calculate-price`，返回的 `discount` 就是这张券的**精确价值** | 券在门店可用、且拿得到券码 |
| 2 | `reverse` | 从菜单反查原价：买一送一/免费券 = 该商品单价；固定价券 = 原价 − 固定价；满减券 = 减免额 | 券码拿不到，但券名能确定对应哪个商品 |
| 3 | `unknown` | **取 `None`，不估** | 上面两条都走不通 |

### 为什么把 probe 放在第一位

实测能拿到**反查拿不到**的价值。本仓库的真实数据里就有一例：

| 券 | 菜单反查 | 实测（`calculate-price`） |
|---|---|---|
| 中薯条买一送一 | ¥13.5 | ¥13.5 |
| **王牌小食拼** | **拿不到**（菜单里没有"王牌小食拼"这个商品） | **¥6.1** |
| 13.9浓浓黑巧 | ¥0（菜单价已经是券后价） | **¥7.1** |

「王牌小食拼」券名里没有数字、菜单里也没有对应商品 —— 只靠反查会把它报成 *价值未知*，
而它实际值 ¥6.1。反查不只是可能低估，**还会把真实存在的价值报成 0**。

### 为什么宁可报"未知"也不估

券名 → 菜单商品的对齐写在 `NAME_ALIGN` 里，**只收录能确定的对应关系**，
不做模糊匹配。本仓库里 `免费脆薯饼` 就落到了"价值未知"——
因为那份菜单快照里确实没有脆薯饼这个商品。

这条与项目其它部分一致：**宁可少报，不可编造。**
`demo.py` 与 CI 都会断言 `face_value is None` 当且仅当 `value_source == "unknown"`。

## 三、券包体检：名义面值不是真实价值

```
净价值 = 券面价值 − 为用这张券、你本来不会花的那部分钱
```

一张「满50减12」，如果基准消费是 20 元 —— 为了用它得点到 50 元，
**名义省 12，实际多花 30，净亏 18**。

| 判定 | 条件 | 含义 |
|---|---|---|
| **顺手可用** | 基准消费已到门槛 | 不用额外多花，白得券面价值 |
| **努一把** | 差额 < 券面价值 | 凑一点仍净赚，标出净赚多少 |
| **纸面富贵** | 差额 ≥ 券面价值 | **明确劝退**，算出硬用会亏多少 |
| **无法判断** | 券面价值未知 | 如实标注，不估算 |

### 基准消费是什么

**基准 = 求解器给出的这一单方案总价**（你本来就要花的钱）。
这是订单作用域的口径，不需要任何订单历史就能跑通。

也可以用 `--baseline` 手动指定，看不同消费水平下判定怎么翻转：

```bash
python scripts/coupon_doctor.py --baseline 20     # 此时「满50减12」会被判为纸面富贵
python scripts/coupon_doctor.py --baseline 60     # 同样一张券变成顺手可用
```

## 四、用券排程：可实现的券，未必用得上

"可实现 ¥26.7"有个隐含前提 —— **这些券你都有机会用掉**。但券会过期，而你的点单次数有限。

```
窗口 = 券全部过期前的天数（只算手里已领、有正净价值、且有效期已知的券）
可点单数 K = max(1, floor(窗口天数 × 每周点单频率 / 7))
```

把净价值从高到低排，前 K 张排进"用得上"，其余就是**注定随券过期浪费的钱**。

**三条假设**（都在这里，不藏在代码里）：

- **A** 基准消费 = 求解器给出的这一单方案总价。
- **B** 窗口内你还会点 K 单，每单最多用 1 张券。**K 里的「点单频率」默认来自订单实测**，
  而不是拍一个数 —— 见下一节。
- **C** 用券不改变你的点单次数。

> 可领取的券**没有有效期**，因此不进排程 —— 把"未知"当成"永久"就是编造。
> 渲染时也不输出它的"剩余天数"。

## 五、点单频率：假设与实测差多少

上一条假设里的「点单频率」是**整个排程结论的开关**。它错 10 倍，结论就错 10 倍：

| 频率来源 | 本仓库的例子里 K | 结论 |
|---|---|---|
| 假设 3 单/周 | 2 单 | 用掉 ¥20.6，浪费 ¥6.1 |
| **订单实测 0.26 单/周** | **1 单** | 用掉 ¥13.5，浪费 **¥13.2** |

同一个券包、同一个窗口，只因为频率从"假设"换成"实测"，**注定浪费的金额翻了一倍多**。

所以默认走实测：`coupon_doctor.py` 从脱敏订单摘要
（[`data/raw/orders_summary_1420762.json`](../data/raw/orders_summary_1420762.json)）
派生 `orders_per_week`。优先级是：

```
--orders-per-week 显式指定  >  订单实测  >  3 单/周 的兜底假设
```

想回到纯假设模式用 `--no-orders`；想换成自己的订单用 `--orders 你的摘要.json`。

### 审计只统计「订单已完成」

- 已取消的订单**不计入** —— 取消的单不代表真实消费。
- 金额为 0 的订单（兑换/活动单）**计入点单频率**（它确实是一笔点单），
  但**不计入客单价**（它没花钱）。两者分开算，不混为一谈。
- 频率 = 已完成单数 ÷ （快照时点 − 最早一单）跨度周数。

### 仓库里没有原始订单

只提交派生指标（客单价、频率、单数、跨度）。
**逐单明细、商品名、下单日期都不在仓库内**，也没有任何订单号或门店信息。
本地留存的完整脱敏快照被 `.gitignore` 排除；连脱敏本身也做了取舍 ——
去掉订单号、门店、BE 码与下单时刻的时分秒。见
[`data/raw/README.md`](../data/raw/README.md)。

## 六、可领取券：唯一零成本的省钱来源

`available-coupons` 会同时返回「已领取」和「还没领」的券。未领取的券是唯一一种
**零成本**的省钱来源，所以也做进体检，沿用同一套净价值框架。

> ⚠️ **不擅自替用户领券。** 领取（`auto-bind-coupons`）会改动账号状态，
> 必须先取得用户明确同意。本工具负责把"有哪些没领、值不值"摆清楚，领不领由用户决定。

## 七、边界

- 券的可用范围、有效期、叠加规则**以门店与 App 实时结果为准**。
  本文所有结论都是快照口径，用于说明算法，不构成下单承诺。
- 「净价值」模型是一个**保守近似**：它假设你按菜单价衡量拿到的商品。
  这是一个可讨论的假设，欢迎在 issue 里反驳。
- 本模块与服务商无关，纯本地计算，不联网。
